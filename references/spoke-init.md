# /bestest init

## Purpose

Full audit and scaffold of the testing infrastructure for a multi-language repository (JS/TS, Python, Java, Go). This spoke detects the technology stack, recommends a test framework, generates configuration, creates the `.bestest/` directory structure, produces the initial `TESTING.md` at the repo root, and installs dependencies. Every decision is documented with rationale and gated by the user before files are committed.

## Prerequisites

- A valid JS/TS, Python, Java, or Go repository — must contain `package.json` (JS/TS), `requirements.txt`/`pyproject.toml`/`setup.py` (Python), `pom.xml`/`build.gradle`/`build.gradle.kts` (Java), or `go.mod` (Go) at the project root. Projects without these files are outside the supported ecosystems and will be rejected with a clear message.
- No existing `.bestest/` directory — if one is found, stop and suggest running `/bestest doctor` instead to validate the existing setup.
- Git is recommended but not required — a dirty working tree triggers a warning, not an error.

## Pre-Flight Checks

Run these checks before starting any detection work. They guard against invalid states and give the user early feedback.

> See **references/pre-flight-protocol.md** for the standard 3-step `.bestest/` validation pattern and spoke-specific variants.

### 1. Check for existing `.bestest/`

```
If .bestest/ exists:
  If --force (or --reinit) was provided:
    Print: "⚠ --force provided. Reinitializing — removing existing .bestest/ and regenerating."
    Proceed to Step 2. (Existing state, reports, and TESTING.md will be lost. The old .bestest/
    directory is preserved at .bestest.bak-<timestamp> before removal for safety.)
    Create the backup: cp -r .bestest .bestest.bak-$(date +%s)
  Else:
    Print: "A .bestest/ directory already exists. This suggests testing infrastructure has been set up before."
    Print: "Run /bestest doctor to validate your existing setup, or run /bestest init --force to reinitialize,"
    Print: "or delete .bestest/ to start fresh."
    Exit. No files created or modified.
```

### 2. Check for project manifest

```
Check for the following files at the project root (in order):
  1. package.json → JS/TS ecosystem
  2. pyproject.toml → Python ecosystem (modern)
  3. requirements.txt → Python ecosystem (classic)
  4. setup.py → Python ecosystem (legacy)
  5. go.mod → Go ecosystem
  6. pom.xml → JVM ecosystem (Maven)
  7. build.gradle or build.gradle.kts → JVM ecosystem (Gradle)

If none found:
  Print: "No supported project manifest found. /bestest init requires a JS/TS, Python, Java, or Go project."
  Print: "Looked for: package.json, pyproject.toml, requirements.txt, setup.py, go.mod, pom.xml, build.gradle"
  Print: "Supported ecosystems: JavaScript, TypeScript, Python (pytest, unittest), Java (JUnit 5), Go (testing, testify)"
  Print: "If this is a different ecosystem (Go, Ruby), support is planned but not yet available."
  Exit.
```

### 3. Check git status (informational)

```
If git is initialized:
  Run: git status --porcelain
  If output is non-empty:
    Print: "Warning: You have uncommitted changes. Consider committing or stashing before init."
    Print: "Init will create new files but will not modify existing ones."
    Continue — this is a warning, not a blocker.
  Else:
    Continue silently.
Else (no .git directory):
  Print: "Note: No git repository detected. Init will proceed, but version control is recommended."
  Continue.
```

## Version Compatibility Check

Before starting detection, verify that the `.bestest/config.yaml` version is compatible with this skill version. This check prevents subtle mismatches from config files generated by older skill versions. See `references/schema-contract.md` for the full version policy.

```
1. Read the version field from SKILL.md frontmatter (if present). This is the current skill version.
2. Read the version field from .bestest/config.yaml (if the file exists — it may not during first init).
3. Compare versions:
   If config version is older than skill version:
     Print: "⚠ Version mismatch: .bestest/config.yaml was generated by bestest v{config_version}, but the current skill is v{skill_version}."
     Print: "  Some config fields may be missing or use outdated schemas."
     Print: "  Run /bestest doctor to validate and migrate your configuration."
     Print: "  Continuing with init will overwrite the existing config."
   If versions match:
     Continue silently.
   If config has no version field:
     Print: "Note: .bestest/config.yaml has no version field. It may predate version tracking."
     Print: "Run /bestest doctor to validate your configuration against the current skill version."
```

After generating `.bestest/state/stack-profile.json`, set its `schemaVersion` to `"1.3"` per `references/schema-contract.md`.

## Phase 2 — Recommend Framework

Run the framework decision engine from `references/framework-decisions.md`. Select the language-appropriate decision tree based on the primary language in the StackProfile and execute it. The decision tree is deterministic: the same StackProfile always produces the same recommendation.

`framework-decisions.md` is the single canonical source for ALL decision trees — JS/TS, Python, Java, and Go. Do not inline decision flows here.

### StackProfile Updates

Populate these fields in the StackProfile:
- `testFrameworks.recommended` — the recommended test runner
- `e2eFramework.recommended` — the recommended E2E runner (or null for API-only)
- `coverage.recommended` — the recommended coverage provider

### ADR Generation

Generate an Architecture Decision Record at `.bestest/adrs/ADR-001-test-framework.md` using the ADR template from the relevant decision tree. Include:

- **Context**: Languages, build tool, frameworks, existing test framework, monorepo status from the StackProfile.
- **Decision**: The recommended framework with coverage and E2E choices.
- **Rationale**: The specific decision tree path taken with evidence.
- **Consequences**: Specific benefits, any trade-offs, migration effort if changing from an existing framework.
- **Alternatives Considered**: The next-best option from the decision tree and why it was not chosen.

## Phase 7 — Validation Run (Optional)

Offer to execute a validation run to verify the entire pipeline works end-to-end. This is an optional step that catches configuration issues before the user invests in writing tests.

### HITL Gate

```
### Validation Run

Would you like to run a quick validation to verify the setup works end-to-end?

Options:
  1. Yes — Run /bestest run to execute tests and verify the pipeline (Recommended)
  2. Skip — Everything is set up. You can run /bestest run or /bestest scan later.

Which option? [1-2]:
```

### If user selects "Yes"

Invoke `/bestest run`. This validates:
- Framework is correctly installed and configured
- Test discovery finds test files matching the configured pattern
- Coverage collection works with the configured provider
- Reports are written to `.bestest/reports/` correctly
- Config state is updated after execution

### If the validation run fails

```
Print: "⚠ Validation run encountered an issue."
Print: "  The setup is complete but the test framework may need additional configuration."
Print: "  Run /bestest doctor to diagnose the issue."
Print: ""
Print: "  Common causes:"
Print: "    - Missing coverage provider (npm install --save-dev @vitest/coverage-v8)"
Print: "    - No test files yet (run /bestest generate --untested to create initial tests)"
Print: "    - Framework config needs adjustment (check .bestest/config.yaml paths)"
```

Do not block on failure — the init is still considered successful. The validation run is a best-effort smoke test.

### If user selects "Skip"

Continue to the Next Steps section. No validation is performed.

## Error Handling

### 1. No Supported Ecosystem

**Trigger**: No `package.json`, `pyproject.toml`, `requirements.txt`, or `setup.py` found in the repository.

**Response**: Print a clear message listing supported ecosystems:
```
"This repository does not appear to be a JS/TS, Python, Java, or Go project."
"Looked for: package.json, pyproject.toml, requirements.txt, setup.py, go.mod, pom.xml, build.gradle"
"Supported: JavaScript, TypeScript, Python (pytest, unittest), Java (JUnit 5, Spring Boot), Go (testing, testify), and common frameworks."
"If your project uses a different ecosystem, support may be available in a future release."
```
Exit. No files created.

### 2. Existing `.bestest/` Directory

**Trigger**: `.bestest/` directory already exists at the project root.

**Response**: Do not overwrite or modify any files. Print:
```
"A .bestest/ directory already exists."
"Run /bestest doctor to validate your existing setup."
"To start fresh, delete .bestest/ and re-run /bestest init."
```
Exit.

### 3. Dependency Installation Fails

**Trigger**: The package manager install command returns a non-zero exit code.

**Response**: Do not delete generated files. Print the error, provide manual install instructions, and suggest running `/bestest doctor` after manual installation. The generated config files are still valid — they just need the dependencies installed to function.

### 4. User Rejects Framework Recommendation

**Trigger**: User responds "cancel" to the Phase 3 HITL gate.

**Response**: Exit cleanly. No files are created or modified. Print:
```
"Init cancelled. No files were created. Run /bestest init again when ready."
```

### 5. Monorepo Without Workspace Config

**Trigger**: Multiple `package.json` files detected (e.g., in `packages/*/package.json`) but no workspace config file (`pnpm-workspace.yaml`, `nx.json`, `turbo.json`, `lerna.json`, or `"workspaces"` in root `package.json`).

**Response**: Print a warning and proceed with single-package mode:
```
"Warning: Multiple package.json files detected, but no workspace configuration found."
"This may be an unconfigured monorepo. Proceeding with single-package setup."
"If this is a monorepo, configure your workspace tool first, then re-run /bestest init."
```

### 6. Context7 Unavailable

**Trigger**: `resolve_library` or `get_library_docs` fails or returns no results.

**Response**: Fall back to static templates without modification. Print:
```
"Note: Could not fetch live framework documentation. Using static defaults."
"Generated config may not reflect the latest version of [framework]."
"Run /bestest doctor after installation to validate against your installed version."
```

### 7. Dirty Git Working Tree

**Trigger**: `git status --porcelain` returns uncommitted changes.

**Response**: Print a warning but continue execution:
```
"Warning: You have uncommitted changes in your working tree."
"Init will create new files but will not modify existing ones."
"Consider committing your changes before proceeding for a clean rollback point."
```

### Template Selection Logic

**Language detection first:**

1. If primary language is `python` → use Python decision tree and config-pytest.yaml template.
2. For Python, select template row based on web framework: FastAPI (row 10), Flask (row 11), Django (row 12), or plain Python (row 13).
3. If primary language is `java` → use Java decision tree and config-junit5.yaml template.
4. For Java, select template based on build tool: Gradle or Maven (both use config-junit5.yaml but with different placeholder values for `junit5_build_tool`).
5. If primary language is `go` → use Go decision tree and config-go.yaml template.
6. For Go, select template based on HTTP framework: Gin, Echo, Chi, gRPC, stdlib HTTP, or non-HTTP (all use config-go.yaml but with different placeholder values for `go_http_framework`).

**JS/TS stack selection:**

1. If `monorepo.detected` is true → use monorepo config template (row 8).
2. If `testFrameworks.existing` is `"jest"` and decision tree says keep Jest → use Jest templates (row 5).
3. If `buildTool` is `"vite"` → use Vitest config template. Select framework config variant by frontend library (rows 1, 6, 7).
4. If `buildTool` is `"next"` → use Vitest config template with Next.js variant (row 2).
5. If no frontend library and API framework detected → use Vitest config with API variant (row 3).
6. If none of the above → use Vitest config with Plain TypeScript variant (row 4).

**Java stack selection:**

1. If Spring Boot detected → use JUnit 5 config template. Select build tool variant: Gradle (row 14) or Maven (row 15).
2. If no Spring Boot → use JUnit 5 config template with plain Java variant: Gradle (row 16) or Maven (row 17).

**Go stack selection:**

1. All Go projects use config-go.yaml template.
2. Select based on HTTP framework detected: Gin, Echo, Chi, gRPC, stdlib HTTP, or non-HTTP.
3. Mocking strategy is set based on existing dependencies: gomock (if detected), testify/mock (if detected), or interface_fakes (default).
