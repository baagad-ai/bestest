# CI Pipeline Design Patterns

## Purpose

Reference guide for CI pipeline architecture patterns used by the `bestest ci` command. Covers the 4-stage pipeline model, coverage gates, flaky test handling, multi-language monorepo strategy, and provider-specific conventions for GitHub Actions, GitLab CI, and Jenkins.

This document is the source of truth for CI pipeline design decisions. The spoke-ci.md generation command references these patterns when assembling workflow files from templates.

---

## 4-Stage Architecture

All CI pipelines generated by bestest follow a 4-stage architecture that balances speed, confidence, and resource cost. Each stage has a time budget and gates that must pass before the next stage begins.

### Stage 1: Fast (< 5 minutes)

**Goal:** Catch obvious failures quickly. Give developers near-instant feedback on syntax errors, import mistakes, and simple logic bugs.

**Test types:** Unit tests only. No external dependencies, no network calls, no filesystem I/O beyond temp dirs.

| Language | Command | Notes |
|----------|---------|-------|
| JS/TS (Vitest) | `npx vitest run --reporter=verbose src/**/*.test.{ts,tsx}` | Unit files only, excludes e2e/integration dirs |
| JS/TS (Jest) | `npx jest --testPathPattern='(unit|src)' --verbose` | Uses testMatch patterns from jest config |
| Python (pytest) | `pytest tests/unit/ -m unit -v --tb=short` | Markers or path filtering |
| Java (Gradle) | `./gradlew test --no-daemon` | Default `test` task runs unit tests |
| Java (Maven) | `./mvnw test -Dgroups="unit"` | Requires `@Tag("unit")` annotations |
| Go | `go test -short -v ./...` | `-short` skips long-running tests |

**Coverage gate:** Minimum threshold from `coverage.target` (default: 80%). Pipeline fails if coverage drops below the gate.

**Retry logic:** No retries on fast stage — tests must be deterministic. Flaky tests at this stage indicate a bug in the test, not the CI.

### Stage 2: Medium (< 20 minutes)

**Goal:** Verify component interactions and service boundaries. Tests may use databases, message queues, or HTTP servers spun up within the CI job.

**Test types:** Integration tests. External services are typically testcontainers, in-memory databases, or wiremock stubs.

| Language | Command | Notes |
|----------|---------|-------|
| JS/TS (Vitest) | `npx vitest run --reporter=verbose "tests/integration/**"` | Integration directory pattern |
| JS/TS (Jest) | `npx jest --testPathPattern='integration' --verbose` | Integration path filter |
| Python (pytest) | `pytest tests/integration/ -m integration -v --tb=short` | Integration markers or paths |
| Java (Gradle) | `./gradlew integrationTest --no-daemon` | Custom integrationTest task |
| Java (Maven) | `./mvnw verify -Dgroups="integration"` | Failsafe plugin for integration |
| Go | `go test -v -tags=integration ./integration/... ./itest/...` | Build tag or path filtering |

**Coverage gate:** Stage-level coverage check. Integration tests often cover different code paths than unit tests; the combined coverage from Stage 1 + Stage 2 should approach the target threshold.

**Retry logic:** Up to 2 retries for known-flaky integration tests (network timing, container startup ordering). See Flaky Test Handling below.

### Stage 3: Slow (< 60 minutes)

**Goal:** End-to-end validation of complete user flows through the real application stack. These tests are expensive but catch system-level regressions.

**Test types:** E2E tests using Playwright, Cypress, Selenium, or similar browser/API automation.

| Language | Command | Notes |
|----------|---------|-------|
| JS/TS (Vitest) | `npx vitest run --reporter=verbose "e2e/**"` | E2E directory pattern |
| JS/TS (Jest) | `npx jest --testPathPattern='e2e' --verbose` | E2E path filter |
| JS/TS (Playwright) | `npx playwright test` | Separate Playwright runner |
| Python (pytest) | `pytest tests/e2e/ -m e2e -v --tb=short` | E2E markers or paths |
| Java (Gradle) | `./gradlew e2eTest --no-daemon` | Custom e2eTest task |
| Java (Maven) | `./mvnw verify -Dgroups="e2e"` | Failsafe with e2e group |
| Go | `go test -v -tags=e2e ./e2e/... ./tests/e2e/...` | Build tag or path filtering |

**Coverage gate:** No coverage gate on E2E stage — these tests exercise code already covered by Stage 1 and 2, but through different execution paths. The value is flow correctness, not coverage percentage.

**Retry logic:** Up to 2 retries. E2E tests are inherently flaky due to browser rendering, network latency, and timing. The retry count is configurable via `flaky.retries` in config.yaml.

### Stage 4: Quality (Nightly / On-demand)

**Goal:** Deep quality analysis that is too expensive for every commit. Mutation testing, full security scans, performance benchmarks, and cross-platform matrix builds.

**Test types:** Mutation testing (Stryker), nightly full-suite runs, chaos experiments.

| Language | Command | Notes |
|----------|---------|-------|
| JS/TS (Stryker) | `npx stryker run` | Mutation testing |
| Python (mutmut) | `mutmut run --paths-to-mutate=src/` | Mutation testing |
| Java (Pitest) | `./gradlew pitest` or `./mvnw org.pitest:pitest-maven:mutationCoverage` | Mutation testing |
| Go | `go test -v -race -coverprofile=coverage.out ./...` | Full suite with race detection |

**Trigger:** Scheduled (nightly cron) or manual workflow dispatch. Never runs on every push.

**Coverage gate:** Mutation score threshold from `mutation.threshold` (default: 80%).

## Coverage Gates

### Configuration

Coverage gates read from `.bestest/config.yaml`:

```yaml
coverage:
  enabled: true
  target: 80        # Percentage threshold
  provider: v8      # Coverage instrumentation
  reporters:
    - text
    - json-summary
    - html
```

### Gate Implementation Per Provider

**GitHub Actions:**
```yaml
- name: Coverage Gate
  run: |
    COVERAGE=$(cat coverage/coverage-summary.json | jq '.total.lines.pct')
    echo "Coverage: ${COVERAGE}%"
    if [ "$COVERAGE" -lt 80 ]; then
      echo "::error::Coverage ${COVERAGE}% is below threshold 80%"
      exit 1
    fi
```

**GitLab CI:**
```yaml
coverage_gate:
  stage: medium
  script:
    - COVERAGE=$(cat coverage/coverage-summary.json | python -c "import sys,json; print(json.load(sys.stdin)['total']['lines']['pct'])")
    - echo "Coverage: ${COVERAGE}%"
    - test $(echo "$COVERAGE >= 80" | bc -l) -eq 1
  coverage: '/Coverage: (\d+)%/'
```

**Jenkins:**
```groovy
stage('Coverage Gate') {
  steps {
    sh '''
      COVERAGE=$(cat coverage/coverage-summary.json | jq '.total.lines.pct')
      echo "Coverage: ${COVERAGE}%"
      if [ "$(echo "$COVERAGE < 80" | bc -l)" -eq 1 ]; then
        echo "ERROR: Coverage ${COVERAGE}% is below threshold 80%"
        exit 1
      fi
    '''
  }
}
```

### Multi-Language Coverage Aggregation

For multi-language monorepos, each language computes its own coverage percentage. The overall gate computes a weighted average based on the number of source files per language:

```
overall_coverage = sum(lang_coverage * lang_weight) / sum(lang_weights)
where lang_weight = count of source files for that language
```

If the weighted average falls below `coverage.target`, the gate fails. Individual language thresholds can be set via config overrides.

## Flaky Test Handling

### Principles

1. **Fast stage tests must never be flaky.** If a unit test flakes, fix it or remove it. Retries mask real bugs.
2. **Integration and E2E tests may flake.** External dependencies introduce timing variability. Retries are acceptable here.
3. **Retry count is bounded.** Maximum 2 retries (3 total attempts). If a test fails 3 times, it's a real failure.
4. **Quarantine, don't delete.** Flaky tests should be quarantined (skipped with a tracking issue) rather than deleted. The `bestest doctor` command tracks quarantine status.

### Retry Implementation Per Provider

**GitHub Actions:**
Uses a retry step wrapper. No native retry on individual steps, so the pattern wraps the test command in a retry script:

```yaml
- name: Run E2E Tests (with retry)
  uses: nick-fields/retry@v3
  with:
    timeout_minutes: 15
    max_attempts: 3
    command: npx playwright test
    retry_wait_seconds: 10
```

For a lighter-weight approach without third-party actions:

```yaml
- name: Run E2E Tests (with retry)
  run: |
    for i in 1 2 3; do
      npx playwright test && break || echo "Attempt $i failed, retrying..."
      if [ $i -eq 3 ]; then exit 1; fi
      sleep 10
    done
```

**GitLab CI:**
Uses the native `retry` keyword on job definitions:

```yaml
e2e_tests:
  stage: slow
  retry:
    max: 2
    when:
      - runner_system_failure
      - stuck_or_timeout_failure
  script:
    - npx playwright test
```

**Jenkins:**
Uses the declarative `retry` block:

```groovy
stage('E2E Tests') {
  steps {
    retry(3) {
      sh 'npx playwright test'
    }
  }
}
```

### Configuration

```yaml
# In .bestest/config.yaml
flaky:
  retries: 2            # Max retry attempts (total attempts = retries + 1)
  quarantine: true      # Auto-quarantine tests failing >3 consecutive runs
  track_history: true   # Maintain flake rate history in reports
```

## Multi-Language Monorepo Strategy

### Parallel Job Architecture

In a multi-language monorepo, each stage runs parallel jobs — one per detected language. The stage gate waits for ALL language jobs to pass before proceeding to the next stage.

```
Stage 1 (Fast):
  ├── job: fast-js      (vitest/jest unit tests)
  ├── job: fast-python  (pytest unit tests)
  ├── job: fast-java    (gradlew test)
  └── job: fast-go      (go test -short)
      ↓ (all must pass)
Stage 2 (Medium):
  ├── job: medium-js
  ├── job: medium-python
  ├── job: fast-java
  └── job: medium-go
      ↓ (all must pass)
Stage 3 (Slow):
  ├── job: slow-js      (Playwright)
  ├── job: slow-python
  └── job: slow-java
      ↓ (all must pass)
Stage 4 (Quality):
  └── job: mutation     (scheduled, not per-push)
```

### Language Detection

Languages are detected from the StackProfile at `.bestest/state/stack-profile.json`. The CI generation spoke reads the `languages[]` array to determine which jobs to include:

```json
{
  "languages": [
    { "name": "typescript", "frameworks": ["vitest"], "package_manager": "npm" },
    { "name": "python", "frameworks": ["pytest"], "package_manager": "poetry" },
    { "name": "go", "frameworks": ["testing"], "package_manager": "go_modules" }
  ]
}
```

If no StackProfile exists, the spoke falls back to detecting languages from project files:
- `package.json` → JS/TS
- `pyproject.toml`, `setup.py`, `requirements.txt` → Python
- `build.gradle`, `pom.xml` → Java
- `go.mod` → Go

### Working Directory Per Language

For monorepos with language-specific subdirectories, each job should `cd` into the appropriate directory before running tests:

```yaml
# GitHub Actions example
fast-python:
  runs-on: ubuntu-latest
  defaults:
    run:
      working-directory: services/api
  steps:
    - run: pytest tests/unit/ -v
```

### Artifact Sharing Between Stages

Test results and coverage reports from earlier stages are shared with later stages via CI artifacts:

- **Stage 1 → Stage 2:** Coverage summary JSON (for combined coverage gate)
- **Stage 2 → Stage 3:** Integration test failure logs (for E2E test prioritization)
- **Stage 3 → Stage 4:** Full test results (for mutation test targeting)

## Caching Strategy

### Dependency Caching

Each language caches its dependency directory to speed up CI runs:

| Language | Cache Path | Key |
|----------|-----------|-----|
| JS/TS (npm) | `~/.npm` | `npm-${{ hashFiles('package-lock.json') }}` |
| JS/TS (pnpm) | `~/.local/share/pnpm/store` | `pnpm-${{ hashFiles('pnpm-lock.yaml') }}` |
| JS/TS (yarn) | `~/.cache/yarn` | `yarn-${{ hashFiles('yarn.lock') }}` |
| Python (pip) | `~/.cache/pip` | `pip-${{ hashFiles('requirements.txt') }}` |
| Python (poetry) | `~/.cache/pypoetry` | `poetry-${{ hashFiles('poetry.lock') }}` |
| Java (Gradle) | `~/.gradle/caches` | `gradle-${{ hashFiles('**/*.gradle*', '**/gradle-wrapper.properties') }}` |
| Java (Maven) | `~/.m2/repository` | `maven-${{ hashFiles('**/pom.xml') }}` |
| Go | `~/go/pkg/mod` | `go-${{ hashFiles('go.sum') }}` |

### GitHub Actions Cache Pattern

```yaml
- uses: actions/cache@v4
  with:
    path: ~/.npm
    key: npm-${{ hashFiles('package-lock.json') }}
    restore-keys: npm-
```

### GitLab CI Cache Pattern

```yaml
cache:
  key:
    files:
      - package-lock.json
  paths:
    - node_modules/
```

### Jenkins Cache Pattern

Jenkins caches are typically handled by the agent's workspace persistence. For ephemeral agents, use a shared volume or repository cache.

## Security Considerations

### Secret Management

CI pipelines must never contain secrets in plaintext. Use provider-native secret management:

| Provider | Mechanism | Access Pattern |
|----------|-----------|---------------|
| GitHub Actions | Repository/Organization Secrets | `${{ secrets.SECRET_NAME }}` |
| GitLab CI | CI/CD Variables (masked, protected) | `$SECRET_NAME` |
| Jenkins | Credentials Plugin + withCredentials | `credentials('id')` |

### Common Secrets for Test Pipelines

- `CODECOV_TOKEN` — Coverage report upload
- `NPM_TOKEN` / `PYPI_TOKEN` — Package registry authentication
- `DATABASE_URL` — Test database connection string
- `PLAYWRIGHT_BROWSEr_PATH` — Cached browser binary path

### Branch Protection

Generated pipelines should include branch protection rules:

- **main/master:** All stages must pass. No skip allowed.
- **feature branches:** Stages 1-3 run automatically. Stage 4 is optional.
- **Hotfix branches:** Stage 1 only, with manual gate to Stage 2-3.

## Output File Paths

Generated CI files are written to the paths that `spoke-doctor.md` Phase 8 detects:

| Provider | Output Path | Detection Pattern |
|----------|------------|-------------------|
| GitHub Actions | `.github/workflows/test.yml` | `.github/workflows/*.yml` |
| GitLab CI | `.gitlab-ci.yml` | `.gitlab-ci.yml` (project root) |
| Jenkins | `Jenkinsfile` | `Jenkinsfile` (project root) |

These paths must match exactly — the doctor spoke scans for these specific locations to populate the CI Health dimension.
